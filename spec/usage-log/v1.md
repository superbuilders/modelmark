# modelmark Usage Log, Version 1

| Field       | Value                                                              |
| ----------- | ------------------------------------------------------------------ |
| Status      | Draft                                                              |
| Version     | 1                                                                  |
| Header      | `{"modelmark":"usage","version":1,...}`                            |
| Schema      | [`v1.schema.json`](./v1.schema.json)                               |
| Conformance | [`conformance/`](./conformance)                                    |
| Readers     | modelmark, from the release that first documents `MODELMARK_USAGE` |

## 1. Introduction

modelmark adds lines to each commit an AI agent makes: which agent and model
made it (`Assisted-by`), what the model replies behind it cost
(`Assisted-cost`), and how many tokens they used (`Assisted-tokens`). It reads
the cost and tokens from the agent's own record of its replies. It knows the
records of a few agents. This document defines a record any other agent can
write, so modelmark can cost that agent's commits the same way.

A usage log is one conversation's model replies, one per line, with each
reply's tokens and where it worked.

## 2. Conventions

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be
interpreted as described in [RFC 2119](https://datatracker.ietf.org/doc/html/rfc2119)
and [RFC 8174](https://datatracker.ietf.org/doc/html/rfc8174) when, and only
when, they appear in all capitals.

A **writer** is the agent that produces a usage log. A **reader** is a program
that consumes one, such as modelmark's commit hook. A **reply** is one
response from a model: one request and the answer to it. A **provider** is the
company whose API served the reply, such as Anthropic, OpenAI or Google.

## 3. Finding the log

A writer that wants its commits costed MUST set two variables in the
environment of the commands it runs:

| Variable          | Value                                                                        |
| ----------------- | ---------------------------------------------------------------------------- |
| `MODELMARK`       | The agent's mark: `<agent>:<model>`, optionally `@<effort>`.                 |
| `MODELMARK_USAGE` | The absolute path of the usage log for the conversation running the command. |

A reader MUST NOT read `MODELMARK_USAGE` unless `MODELMARK` is set and is a
valid mark. When `MODELMARK_USAGE` is unset, empty, not absolute, or names a
file the reader can't open, the reader MUST treat the commit as having no
known cost and MUST NOT fail the commit.

## 4. File structure

### 4.1 Encoding and lines

A usage log MUST be UTF-8 text, with no byte order mark. It is a sequence of
lines separated by a line feed (`U+000A`). A line MAY end with a carriage
return (`U+000D`) before the line feed, which a reader MUST ignore. Each
non-empty line MUST be one JSON object ([RFC 8259](https://datatracker.ietf.org/doc/html/rfc8259)),
the layout known as [JSON Lines](https://jsonlines.org). A reader MUST ignore
empty lines.

The file's name is the writer's choice. A `.jsonl` extension is RECOMMENDED.

### 4.2 The header

The first non-empty line MUST be the header:

| Member      | Type   | Requirement | Meaning                                                                                                                          |
| ----------- | ------ | ----------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `modelmark` | string | REQUIRED    | The string `"usage"`.                                                                                                            |
| `version`   | number | REQUIRED    | The integer `1` for this version.                                                                                                |
| `session`   | string | REQUIRED    | The conversation's id: non-empty, the same for every log the conversation writes, and different from every other conversation's. |

```json
{ "modelmark": "usage", "version": 1, "session": "discord:123:456:789" }
```

### 4.3 Reply lines

Every line after the header is one reply. Replies MUST appear in the order
they finished, oldest first, and each reply's `at` MUST be at least one
millisecond later than the one before it. A reader remembers where it stopped
by `at` (Section 6.3), so two replies with the same time could be counted
once between them.

| Member            | Type             | Requirement | Meaning                                                                                                                             |
| ----------------- | ---------------- | ----------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `at`              | string           | REQUIRED    | When the reply finished: an [RFC 3339](https://datatracker.ietf.org/doc/html/rfc3339) date and time with a time zone offset or `Z`. |
| `model`           | string           | REQUIRED    | The model, as its [models.dev](https://models.dev) id (`claude-opus-5-5`, `gpt-6.1-sol`).                                           |
| `input`           | integer          | REQUIRED    | Every input token, including those read from or written to a prompt cache.                                                          |
| `cacheRead`       | integer          | REQUIRED    | The part of `input` read from a prompt cache.                                                                                       |
| `cacheWrite`      | integer          | REQUIRED    | The part of `input` written to a prompt cache.                                                                                      |
| `cacheWriteByTtl` | object           | OPTIONAL    | `cacheWrite` split by how long the provider keeps the entry. See Section 5.2.                                                       |
| `output`          | integer          | REQUIRED    | Every output token, reasoning included.                                                                                             |
| `cwd`             | string           | REQUIRED    | The absolute path of the folder the agent was working in.                                                                           |
| `paths`           | array of strings | OPTIONAL    | Absolute paths the reply's tool calls named, such as files it read, wrote or ran commands in.                                       |

```json
{
    "at": "2026-10-23T17:02:30.951Z",
    "model": "claude-opus-5-5",
    "input": 52651,
    "cacheRead": 51315,
    "cacheWrite": 1240,
    "cacheWriteByTtl": { "1h": 1240 },
    "output": 207,
    "cwd": "/srv/worktrees/ft-1456",
    "paths": ["/srv/worktrees/ft-1456/src/app.ts"]
}
```

`model` names the model that produced this reply. `MODELMARK` names the model
of the reply that asked for the command, so earlier replies in the same log
may name other models. A gateway's prefix, as in
`anthropic-primary/claude-opus-5-5`, is allowed: a reader prices the part
after the last `/`, at the first-party price.

A log holds each reply on one line. The example is spread out to be read.

## 5. Counting tokens

### 5.1 Input and its parts

`input` counts every token the model read for the reply. `cacheRead` and
`cacheWrite` are parts of it and MUST NOT overlap each other:

```text
cacheRead + cacheWrite <= input
fresh = input - cacheRead - cacheWrite
```

`fresh` is the input neither read from nor written to a cache. It is not
written to the log, since it follows from the three counts.

Providers report input differently. Some include cached tokens in their input
count; others report them beside it. A writer MUST convert to this document's
meaning. Appendix A shows the conversion for common APIs, and
[`conformance/providers/`](./conformance/providers) has a worked example for
each.

`output` counts every token the model produced, reasoning included. When a
provider reports reasoning beside its output count, the writer MUST add the
two.

All integers MUST be 0 or greater.

### 5.2 Cache lifetimes

Providers keep a cache entry for a time, and price a write by how long. The
lifetimes and prices differ between providers. `cacheWriteByTtl` records them
as the provider labels them.

Its keys are lifetimes: an integer followed by `s`, `m`, `h` or `d` (seconds,
minutes, hours, days), such as `"5m"`, `"1h"`, `"30m"` or `"12h"`. Its values
are token counts. Its values MUST add up to `cacheWrite`.

When `cacheWriteByTtl` is absent, every token in `cacheWrite` was written at
the provider's default lifetime. A writer SHOULD include `cacheWriteByTtl`
whenever the provider reports a split.

## 6. Reading

### 6.1 The file

A reader MUST reject the whole file, and treat the commit as having no known
cost, when its first non-empty line is not a header as Section 4.2 defines,
including when `version` is any value other than `1`. A reader SHOULD treat
a path that is not a regular file, such as a pipe, as no log, since reading it
could wait forever.

### 6.2 Each reply line

A reader MUST skip a reply line that:

- is not a JSON object,
- lacks a REQUIRED member, or has a member of the wrong type or range,
- has `cacheRead + cacheWrite` greater than `input`, or
- has a `cacheWriteByTtl` whose values don't add up to `cacheWrite`.

The header is never a reply, even when it carries a reply's members. Skipping
covers a final line the writer is still writing. A reader MUST NOT
reject the file because of a skipped line.

A reader MUST ignore members this document doesn't define, in the header and
in reply lines.

### 6.3 Which replies a commit pays for

modelmark applies these rules. Other readers SHOULD.

1. **Since the last commit.** For each session and repository, the reader
   remembers the `at` of the newest reply it charged to a commit. A commit
   pays for the replies after that, up to the commit. A reply MUST NOT be
   charged to two commits.
2. **In this repository.** A reply belongs to the repository that contains
   any of its `paths`, or, when none does, its `cwd`. A reply that belongs to
   another repository, or to none, MUST NOT be charged to this commit.
3. **Amends.** An amended commit keeps the cost and tokens its message already
   has and adds the replies since.

### 6.4 Pricing

Each reply is priced on its own, from its `model`'s prices:

| Tokens                                          | Price                                                    |
| ----------------------------------------------- | -------------------------------------------------------- |
| `fresh`                                         | the input price                                          |
| `cacheRead`                                     | the cache-read price                                     |
| `cacheWrite` at the provider's default lifetime | the cache-write price                                    |
| `cacheWrite` at a longer lifetime               | the input price times that lifetime's multiplier (below) |
| `output`                                        | the output price                                         |

Published price lists, models.dev's included, give one cache-write price: the
default lifetime's. A reader keeps its own table of the other lifetimes'
multipliers. modelmark's table, as of this version:

| Provider  | Default lifetime | Longer lifetimes |
| --------- | ---------------- | ---------------- |
| Anthropic | `5m`             | `1h`: 2×         |
| OpenAI    | `30m`            | `12h`: 2.5×      |

When a charged reply's model has no known price, or its `cacheWriteByTtl`
names a lifetime the reader has no price for, the commit's cost is unknown: a
reader MUST NOT record it as zero, or price the tokens at another lifetime's
rate. The reader SHOULD still record the tokens.

## 7. Writing

1. **Current at commit time.** The log MUST hold every finished reply of the
   conversation by the time a command the writer runs starts `git commit`,
   including the reply that asked for that command. That reply is part of
   the commit's work.
2. **No half files.** A writer MUST either append whole lines, or replace the
   file by writing a new one in the same folder and renaming it over the old
   one. It MUST NOT truncate the file and write it again in place. A reader
   may open the file at any moment.
3. **Readable by the committer.** The file, and each replacement of it, MUST
   be readable by the user that runs `git commit`, and so MUST every folder
   above it. It need not be readable by anyone else.
4. **One conversation per file.** A log MUST hold one conversation's replies.
5. **The reader's memory lasts.** modelmark remembers where each commit
   stopped in `$XDG_STATE_HOME/modelmark`, or the committing user's default
   state folder when that is unset. Every command a conversation runs MUST
   see the same writable state folder. A command given a fresh one sees no
   earlier commit and charges the conversation's earlier replies again.

A writer that keeps the conversation elsewhere, such as in a database, can
meet all five by doing this after it saves each reply and before it runs the
commands that reply asks for: write the whole conversation to a new file
beside the log, close it, give it its final owner and permissions, then
rename it over the log. One conversation's writes must not overlap.

## 8. Versions and extensions

A change that a reader of an earlier version would misread, such as a new
REQUIRED member or a new meaning for an existing one, MUST use a new
`version`. Adding an OPTIONAL member does not, since Section 6.2 has readers
ignore members they don't know. A new cache lifetime needs no new version:
readers add it to their table (Section 6.4).

A writer MAY add its own members. Their names SHOULD start with `x-`, so a
later version of this document can't give the same name another meaning.

## 9. Security and privacy

A usage log names folders and files on the writer's machine and nothing else:
no prompts, no replies, no file contents. A reader MUST treat a log as
untrusted input. It MUST NOT run anything a log names, and SHOULD bound how
much of a large log it reads. A writer SHOULD keep the log out of the
repository it describes, so it isn't committed by mistake.

## 10. Conformance

A file conforms to this version when its first non-empty line validates
against `#/$defs/header` in [`v1.schema.json`](./v1.schema.json), and every
other non-empty line validates against `#/$defs/reply` and meets Section 6.2's
two sums. A writer conforms when every file it writes conforms, it meets
Section 7, and it converts provider counts as Section 5 says. A reader
conforms when it meets Section 6 and gives the result each case in
[`conformance/cases.json`](./conformance/cases.json) expects.

## Appendix A. Converting provider usage (informative)

How to fill a reply line from what each API returns. `conformance/providers/`
holds a worked example of each.

### Anthropic Messages API

Anthropic's `input_tokens` leaves out cached tokens.

| Member            | From `usage`                                                                                       |
| ----------------- | -------------------------------------------------------------------------------------------------- |
| `input`           | `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`                             |
| `cacheRead`       | `cache_read_input_tokens`                                                                          |
| `cacheWrite`      | `cache_creation_input_tokens`                                                                      |
| `cacheWriteByTtl` | `{"5m": cache_creation.ephemeral_5m_input_tokens, "1h": cache_creation.ephemeral_1h_input_tokens}` |
| `output`          | `output_tokens` (includes thinking)                                                                |

### OpenAI Responses API

OpenAI's `input_tokens` includes cached tokens. `cached_tokens` counts reads
only; tokens written to the cache are in `cache_write_tokens`.

| Member            | From `usage`                                                                                            |
| ----------------- | ------------------------------------------------------------------------------------------------------- |
| `input`           | `input_tokens`                                                                                          |
| `cacheRead`       | `input_tokens_details.cached_tokens`                                                                    |
| `cacheWrite`      | `input_tokens_details.cache_write_tokens` (absent on models without write charges: use 0)               |
| `cacheWriteByTtl` | `{"30m": ttl_30m_tokens, "12h": ttl_12h_tokens}` from `input_tokens_details.cache_write_tokens_details` |
| `output`          | `output_tokens` (includes reasoning)                                                                    |

### OpenAI Chat Completions API

For models without cache-write charges (GPT-5.5 and earlier). OpenAI doesn't
document how Chat Completions reports cache writes for later models; use the
Responses API for those.

| Member       | From `usage`                             |
| ------------ | ---------------------------------------- |
| `input`      | `prompt_tokens`                          |
| `cacheRead`  | `prompt_tokens_details.cached_tokens`    |
| `cacheWrite` | `0`                                      |
| `output`     | `completion_tokens` (includes reasoning) |

### Google Gemini API

Gemini's `promptTokenCount` includes cached content. It reports reasoning
beside its output count.

| Member       | From `usageMetadata`                                                  |
| ------------ | --------------------------------------------------------------------- |
| `input`      | `promptTokenCount + toolUsePromptTokenCount`                          |
| `cacheRead`  | `cachedContentTokenCount`                                             |
| `cacheWrite` | `0` (explicit caches are billed for storage over time, not per reply) |
| `output`     | `candidatesTokenCount + thoughtsTokenCount`                           |
